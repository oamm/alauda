# Storage Providers

Alauda supports PostgreSQL and SQLite through the persistence layer. Repositories and public APIs use the same logical records for both providers.

## Configuration

```yaml
storage:
  provider: postgres
  connectionString: "postgres://alauda:password@db:5432/alauda?sslmode=require"
```

The equivalent environment variables are `ALAUDA_STORAGE_PROVIDER` (`postgres` or `sqlite`) and `ALAUDA_DATABASE_URL`. `REGISTRY_STORAGE_PATH` remains supported for older SQLite deployments. Provider selection defaults to PostgreSQL. Environment values override YAML settings; the development script sets both variables from its `--db` selection.

For SQLite, use a persistent file:

```yaml
storage:
  provider: sqlite
  connectionString: "./data/alauda.db"
```

SQLite enables foreign keys, WAL journaling, and a five-second busy timeout. The file's directory is created by the server. SQLite is supported for local use, tests, demos, and single-node deployments with low or moderate write volume. It is not suitable for multiple Alauda replicas, HA, or workloads that need PostgreSQL's write concurrency.

## Development

The recommended development workflow uses PostgreSQL. `scripts/dev.sh` delegates to the existing `scripts/run-app.ps1` bootstrap workflow and accepts the same provider choice:

```sh
./scripts/dev.sh
./scripts/dev.sh --db postgres
./scripts/dev.sh --db sqlite
```

The PostgreSQL path starts only the `postgres` service from Docker Compose, waits for its healthcheck, applies migrations, then starts Alauda. The script uses the active Docker context endpoint as the database host for remote Docker contexts; set `ALAUDA_POSTGRES_HOST` to override it and `ALAUDA_POSTGRES_PORT` to select the published port. Local Docker uses `localhost`. Local-only credentials are in `docker-compose.yml`. SQLite starts no container and persists at `.artifacts/alauda-dev.db`.

To rotate the local bootstrap credential, add `--reset-dev-password`; the existing database and records are preserved.

To run storage tests locally, use `go test ./...` for SQLite coverage. To include PostgreSQL migration and repository smoke coverage, start the Compose service and set `ALAUDA_TEST_POSTGRES_URL` to its connection URL before running `go test ./internal/storage`.

## Migrations

The migration runner applies the shared ordered migration sequence transactionally and records each filename in `migrations`. SQLite uses the existing migration SQL; PostgreSQL has provider-specific fragments for migrations 005 and 023 to preserve the logical schema while using portable physical types and chronology indexing. PostgreSQL uses native boolean columns and partial indexes. IDs are generated by the application as UUID strings. JSON documents are serialized as text in both providers, with JSON operations adapted inside storage.

## Production And Backups

PostgreSQL is recommended for production clusters, multiple server replicas, HA, high concurrency, and larger operational histories. Configure TLS and credentials through a secret manager or protected environment variables. The application never starts Docker or provisions a database at runtime.

For PostgreSQL, use database-native backups and test restores. For SQLite, prefer the online backup API. If copying files directly, stop or quiesce the server and account for the database, WAL, and shared-memory files together. Keep SQLite data on a local filesystem with reliable locking; do not share the database file across hosts.

Some SQL remains provider-specific inside `internal/storage`: PostgreSQL placeholder syntax, JSON extraction/update, boolean literals, timestamps, and conflict handling are adapted there. SQLite remains a single-writer database, so a higher write rate may increase request latency even with WAL enabled.
